keelson-rib-chat · swarms surface · design, iteration two

A Swarms tab that leads with the decision

What the tab shows a human at three moments: a glance across every swarm, one swarm open, and a launch. Built on the surface that shipped in 0.9.0 and the canvas vocabulary Keelson 0.111 renders.

The index as an operator sees it, at application size. Within a glance: one swarm needs a decision and says which, one is running and how far into its budget, and three have ended with their outcomes.

Today the tab shows the mechanism before the decision. A live card lists channel, roster, project, size, model and start time, and puts what the swarm is doing, or what it needs from you, in a muted line at the bottom. The board opens on five rows of setup and an empty Runs column that takes the wider half of the width. The meter reads as progress when it measures budget. A worker waiting for a free slot and a worker that has finished both say idle. The three launch tabs mix what a swarm may do with how you prepare it, and switching tabs discards the task you typed.

This iteration reorders each surface around one question. At the index: what needs me, and what is running. On a board: what should I read or decide now. In the launcher: can this swarm do my task, and what will it cost. It adds a budget strip, a bench of agent cards with open seats, a single launch form, a request ladder that tracks each question separately, and one vocabulary across the tab, the tool and the docs. Nearly all of it is the rib recomposing primitives the canvas already renders; six host additions are named and ranked in appendix D, each with what the tab does until it lands.

Two rules run through every surface. The thing the operator must act on is the largest text on its card, with its own verb. A meter is named as budget and sits apart from the line that says what is happening, so a fuller bar never reads as more done.

It does not add a transcript to the tab, approval buttons that share the lead's grant, or a second home for runs; decisions D1 to D5 and the alternatives in the first design stand. chat_swarm_start, the swarm's routing and its limits do not change. The host additions are proposals, not dependencies: every surface below renders on 0.111 as drawn, and the table in appendix D says what each addition improves.

Three moments

An operator comes to the tab for one of three reasons, and each surface is built for one of them. Nothing on a surface should make the operator work out the answer to its question.

The index

A live card answers the glance question in its first line. When the swarm needs the operator, the request is the title and its verb is the primary action: Review plan for a gate the rib knows, Answer for one it does not, Read question for an agent's question. The task the request belongs to drops to the footnote. When nothing is asked, the title is the task, the first line is what the swarm is doing this minute, and the budget sits below it as a named meter. Setup is one muted line in both cases. Stop stays in the card's overflow menu.

The host renders card parts in a fixed order: title, meter, fields, footnote, reason, actions. The design works inside that order and puts nothing that matters in reason, which the host draws small, muted and italic: it carries only +2 more requests. A request card has no meter, so spend never sits between the request and its explanation.

Three levels of text

Every card and row uses three levels and no more. The first is the decision or the current activity: the title on a request card, the first field on a running card. The second is supporting context: why the request is yours, what the budget is. The third is metadata: task, project, size, model, roster, start time, in the footnote. Meaning is carried by level, never by a small shift in gray, and nothing an operator must act on is below the second level.

Emphasis is spent once per index. The card with the oldest request is the one with a toned edge; running cards keep the host's plain border; ended swarms are rows. Dashed strokes mean one thing on the tab, an open seat on the bench. Until the host can tone a card's edge (appendix D), the request card's pill and title tone carry the emphasis.

Fields on a card render as one inline row joined by dots, so each line above is one field with no label. The host wraps a long field; the rib keeps each under about 70 characters. The meter's name and remainder are one field above the track until the host draws a label on the bar itself.

Requests

"Needs you" is one word for four different situations, and today they share one card, one primary action and one way of clearing. Any message from a human clears every open question at once, so an unrelated note to the lead can silently dismiss two questions the operator never read. The ladder below gives each kind its own pill, its own first action, and its own clearing rule. The count in the header, the badge and the card's +N more all use the same list, in the same order.

A question card carries the same Reply field a gate card does, posting in the question's thread as the operator. Replying in a thread does not approve anything; the card says so under the field. Steering the lead clears only questions the lead itself asked.

The swarm board

The board has two orders, one for a live swarm and one for an ended swarm, because the operator's question differs. Live, the request comes first, then the budget, then the way to reach the lead. Ended, the outcome comes first, then the result in numbers. The record, meaning agents, task, context, activity and setup, follows in both and reads the same in both, so an operator who learns the live board knows the ended one.

The two-column layout goes. A Discuss swarm has no runs, so the Runs section appears only when the launch named workflows, and it says so when none has started yet: The lead may start fix-issue; none started.

Budget and the bench

The stats section gives the board four tiles that carry the numbers an operator reads first. Turns is budget, so its sub line says what is left, and a sparkline of turns per minute from the activity log shows whether the swarm is accelerating or idling. Time counts against the wall clock. Agents counts seats. Tokens shows fresh tokens as the value and cached as the sub line, and that split is the one used everywhere on the tab: the two are never summed, because a cached token costs a fraction of a fresh one and a sum hides the spend.

The agents become a bench: a cards grid with one card per agent and a dashed ghost card for each open seat up to the swarm's cap, so the capacity the operator paid for is visible. Each card is the agent's handle in its identity color, a status pill, its turn meter against the per-worker cap, its role, its tokens, and a footnote with its last event. The lead's card has no meter, since the swarm budget bounds it.

A pinned model shows on the bench only when it differs from the swarm's, so the role always has the room. The identity color never appears without the handle beside it.

Reaching the lead, and stopping

The Steer form becomes Message the lead, with the placeholder Posts in #swarm-st4j8 as you and wakes the lead · Enter sends, because that is what it does and "steer" suggested a private control. The success toast says where it was posted. Stop stays on the same actions row, destructive and confirm-guarded, pinned to the far end with align: "end" so it is not the next thing under the text field. The confirm names the runs it cancels, as today, and the board shows stopping until the child runs are cancelled and the tokens revoked, then the lifecycle word; today it says stopped before that work is done.

Outcome and result

The header pill on an ended board is the lifecycle: done, stopped, stalled, out of budget, failed. Today it can read PR #41 verified on a swarm that was stopped with two other runs abandoned. The result strip carries the verified count as its own tile, 1 of 3 runs verified, and the outcome card of a swarm that did not conclude names the cause in its title: Stopped by you at 21:50, Out of turns at 40, Failed: ClickClack unreachable. Run again keeps its size, power and model fields and gains a hint that says what it reuses, including how many context items and when they were captured, so an operator does not rerun stale evidence by accident.

Task and context

The board's title truncates the task to its first line and nothing on the tab shows the rest. A Task row with the full task as its disclosure fixes that with a primitive the host has: a row's detail holds 4,000 characters of plain text, and the tool caps a task at 8,000, so a task past 4,000 shows its first 4,000 with Read in full opening the reading pane. Each context item becomes a row the same way: kind and title, the source link, the retrieval time and the commit it was taken against, with the item's text under the disclosure. The operator can check what the agents were given without leaving the board.

The launcher

The three tabs go. Discuss and Dispatch are the same form with one field different, and In chat is not a kind of swarm but a way to prepare one. One form replaces them, and the mode falls out of one field: a swarm with no workflows named investigates, and a swarm with workflows named may dispatch them. That removes the tab switch that discards a typed task, and it needs nothing from the host. Prepare in chat sits beside Start as a second button.

The size segments carry their numbers because the words alone do not say what a choice costs. The hover still lists every limit. Prepare in chat opens the chat that gathers issue bodies, diffs and reviews, then calls chat_swarm_start, as In chat does today.

The ClickClack footer

The footer's head is visible while it is folded, and today the head shows only whether the server is running while a start, stop or reset in progress reports in the body the operator has folded away. The head's pill takes the operation: starting…, stopping…, reset failed, then back to running or stopped. Diagnostics stay in the body: address, process, binary, data directory, the log. An external server gets a reachability probe on each refresh, so its pill reads reachable or unreachable since 21:40 with a Retry action, where today it reads running whether or not anything answers. The list of workflows whose approvals the host keeps for the operator moves to the launcher, under the Workflows field, where the decision it informs is made.

Validation

Every board is a pure function of the swarm summary, so the builders are tested against fixture summaries, one per state the design names: running with no request, each of the four request kinds alone, decide and question together, a waiting agent beside a busy one, a Discuss swarm with no Runs section, a Dispatch swarm with workflows named and none started, ended done with a report, ended stopped with one of three runs verified, and a failure before boot. Each frame passes expectView(key, "board"), the validator the host applies before it broadcasts, so a vocabulary slip fails a test rather than blanking the tab.

The launcher's evidence refusal is tested at the action: a task with a URL and no context returns the inline error and starts nothing; the same task with a context item starts. The request ladder is tested at the rib: two open questions, a reply in one thread, and the other stays open. The live smoke test asserts the index frame's pills and primary actions as a scripted swarm moves through starting, running, a gate in review, a gate only the operator can answer, and done. A manual pass in the browser at 1200 and 640 pixel widths, with the boards screenshotted in both themes, goes in the PR.
