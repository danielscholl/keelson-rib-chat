A Swarms tab for the chat rib

What the chat rib shows inside Keelson: one tab that says which swarm needs you, what each swarm is doing, and what it produced. The conversation stays in ClickClack.

Today a swarm has no home in Keelson. The rib publishes no surface, and Keelson renders nothing for durable ops, so the only live view is the swarm's ClickClack channel. An operator running three swarms finds the one waiting on a gate, or the one that went quiet, by walking channels one at a time. Only the last 20 ended swarms are kept, in memory, and a restart loses them.

This change adds one Keelson tab, Swarms. A live index sorts swarm cards by whether they need you. A drawer board per swarm shows its gate, dispatched runs with their evidence, and its agents, with steer and stop. A markdown reading pane shows a conclusion or a gate prompt, and a history drawer reads ended swarms from disk. Each swarm starts with a size (small, medium or large) and a power (fast, balanced or deep), and every card names both along with the model its agents run. Tiers 1 and 2 use only board primitives in @keelson/shared 0.110.0, so they are rib-side only.

The tab does not copy the transcript, answer approval gates, or open a run's trace. Every channel, gate thread and ask links out to ClickClack. A gate only you can answer is flagged here and answered in the Workflows tab until Keelson gains an effect that opens an existing run. Power, and hover text on each size and power, wait on small host changes. Five decisions are open at the end of the page.

Colors in the diagrams identify who owns each part

Keelson host · renders tabs, the drawer, runs and approvals Chat rib · tracks swarms, publishes boards, handles actions ClickClack · holds the conversation, threads and bots Operator · reads, steers, answers what needs them

The mockups use Keelson's own palette and reproduce its board primitives from apps/web/src/app.css. Every element maps to a section kind in packages/shared/src/canvas.ts; identifiers and times are example values.

What the tab is for

ClickClack holds the conversation, one channel at a time, and knows nothing about runs, gates or verification. Keelson's Workflows tab already inspects runs node by node. The Swarms tab covers what neither does, which is the state of every swarm at once and what each one produced.

The Swarms index

The tab has one region, the index. Its head carries the only count on the page: 2 need you when any swarm needs the operator, otherwise 3 live, otherwise nothing. Live swarms are cards, sorted with the ones that need you first (oldest need first), then starting, then running. Ended swarms are rows, newest first, capped at eight with a row that opens the rest. The tab is titled Swarms because Keelson already has a Chat tab.

Needs you

A swarm needs you when it cannot make progress without the operator. Four conditions raise it, in this order of precedence on the card; the drawer lists every one that holds.

ConditionRaised whenClears when
N4ClickClack stopped answeringThe swarm's socket closes twice with no open in between, at least 4 s at the 2 s retry.The socket opens.
N1A gate only you can answerThe lead's respondToRun on this workflow was refused under ribApprovalGrants. The refusal is remembered per workflow, so the next gate raises it at once.The run resumes or ends; a later successful answer on that workflow forgets the refusal.
N2A gate nobody is working onA run is paused and the swarm went fully idle after the gate opened, with no turn since.Any turn starts or the gate closes.
N3An agent asked you 1bA bot message contains @operator, or the owner's handle when one is set.You post in the channel, steer the lead, or the swarm ends.

The gate is the case that matters most, because a paused run holds the whole swarm open. When the swarm is granted approvals for the workflow, the gate never needs you: a peer reviews the plan in the gate thread and the lead answers.

N2 watches the whole time a gate is open. The swarm does not nudge its lead while any run is live, and a paused run counts as live, so without N2 a reviewer that never replies would hold the swarm silently until the wall clock ends it.

The drawer shows the gate as a card. Its title, pill and reason change with the condition; the thread link and the run id are always there.

Swarm drawer

Open on a card or a row returns open-canvas to the swarm's own board key, rib:chat:swarm:<id>, which Keelson shows in its full-screen drawer. The board is live over the same snapshot socket as the index. It has exactly one actions section, so the steer field keeps what you typed while frames arrive.

Evidence strip

Each run row carries a three-part strip that follows the rib's own verified rule. An isolated run shows worktree, PR and CI: green once each holds, red on an isolation breach or failing CI, and hatched when the run settled without a readable CI verdict. A run in the live checkout needs no PR, and only failing CI blocks it, so it shows a single CI segment that is never hatched. Run rows link to the gate thread while paused and to the first PR after; they carry no disclosure, because a row whose text changes closes any disclosure the reader had open.

Agents get identity colors in spawn order: the lead is brand, workers take the five identity hues, and a sixth worker onward is neutral with its name. Inside a drawer the chips drop the swarm-id prefix from each handle, since the head already names the swarm, and the role text stays short so the column holds at half width. Busy, capped and failed show as the row glyph. When the lead and workers run different models, each agent row shows its model in place of its role text; otherwise the model row in the vitals covers them all. The host does not render a roster peek in the drawer head, so the Agents column is the roster.

Reading pane

Board text is plain: row details and card fields render markdown source as literal characters. A formatted conclusion or gate prompt therefore opens in a markdown drawer view, rib:chat:doc:<id>, one per swarm, reached from Read in full and Read the gate. Its content depends only on that swarm's state, so two viewers reading different swarms never race on one key.

  • Conclusion filed or swarm ended: the task as a heading, a byline, then the conclusion. With no conclusion, the refused draft under a quote that names why it was refused.
  • Live with a gate open: each open gate's prompt as a quote, plus its files in tier 2.
  • Otherwise: one line pointing to the channel.

The markdown drawer has no buttons, so the pane is read-only. Its view entry is declared once when the swarm registers, which costs one manifest refresh per swarm start.

How the tab stays live

Every region is push: the rib holds all swarm state in process, so there is no collector workflow and no cadence. A swarm reports each change, and the rib recomposes the keys that change touches: always the index, always that swarm's board, the reading pane on a gate, conclusion or end, and history on an end.

Top: state flows from ClickClack and workflow runs to the tab. Bottom: actions flow back. A recompose requested while one is in flight is dropped by the host, so each key's publisher keeps a dirty flag and loops until the latest state has landed.

  • Keys outlive swarms. A client that gets a 404 on a key stops listening for good, so a swarm's keys stay registered after it ends. One that ages out of history recomposes to a notice pointing at its channel, and keys are released only at dispose or past a cap of 100.
  • Frames are whole. Each version replaces the payload, so the boards are bounded: the index under 16 KB, a swarm board under 48 KB (12 agents, 12 runs), the reading pane under 96 KB.
  • Times are absolute. Push regions get no "updated 2m ago" label and a relative time would freeze between frames, so the tab shows HH:MM, with a date on ended swarms.
  • State is shared. Actions carry no viewer identity, so the tab keeps no per-viewer selection, and anything one viewer clears clears for all.

Size and power

A swarm starts with two choices. Size bounds how much it may do: agents, turns, time and how many turns run at once. Power picks the model its agents run on. Both appear as words on the tab and in the form. The numbers and model ids show in the drawer, and on hover once the host carries option hints.

SizeAgentsTurnsPer workerAt onceWall clockPer turnSuited to
small3208215 min5 minA question, a doc check, a review of one change
medium54012330 min5 minAn issue investigation, or a fix with one dispatched run
large88016460 min10 minSeveral dispatched runs, or wide reading across a project
  • Medium is today's defaults. A start with no size behaves exactly as it does now, so existing callers and the chat-swarm workflow see no change.
  • Size is the base, explicit limits override it. chat_swarm_start gains size, and max_agents, max_turns and the other limits still set single numbers on top of it. The label is worked out from the effective limits, so a swarm whose limits match no size shows custom and the drawer lists its numbers.
  • Size also sets concurrency. Today three turns run at once at every size, so a larger swarm adds breadth but not speed. Concurrency stays off the tool inputs and moves only with size.
  • The chat-swarm workflow stays medium. Its wait loop covers 40 minutes, less than a large swarm's hour, and it takes no inputs.
PowerKeelson model classOn Copilot, with the map belowSuited to
fastfastmai-code-1.1-flashSummaries, triage, checks against a list

  • Power is a Keelson model class. The words are the same fast, balanced and deep that workflow nodes use, so one map in config.json serves workflows and swarms. Every agent in the swarm runs the power's model.
  • An exact model overrides power. The form's model picker sets one model for every agent, and its empty row reads use power. The tool's model and worker_model still split lead and workers for callers who want that.
  • No power and no model is the provider's default. That is today's behavior, and the card reads copilot default once the first turn reports its provider.
  • Copilot needs the map. Copilot publishes all three classes as auto, so power changes nothing there until config.json maps them; appendix G has the map for the three models above. Keelson reads it at boot, so a restart applies it. Claude and Codex derive their classes from their own catalogs.

Power needs one host change. A rib's agent turn hands its model string to the provider unchanged, and only workflow nodes resolve a class name, so a swarm that asked for deep today would send the literal id deep and fail its turns. So power arrives on the tool and the form in the rib release that raises its peer floor to the host version that resolves classes on rib turns. Until then the form offers the model picker alone.

Validation

The boards are pure functions of the swarm summary. Each builder is tested against fixture summaries covering first run, starting, running, gate in review, N1, N2, N4, ended done, ended stalled, and a failure before boot. Every frame must pass expectView(key, "board"), the validator the host applies before it broadcasts, so a schema slip fails a unit test instead of blanking the tab.

A publisher test checks that a change landing during an in-flight recompose is published by the next loop. dev/live-smoke.ts gains assertions on the index frame as a scripted swarm moves through starting, running, gate, answer and done against a real ClickClack, with no model spend. Last, a manual run of the fix-issue scenario with the tab open, then again with ribApprovalGrants.chat removed, confirms that N1 appears and clears once the run is answered in the Workflows tab.

Size tests check that each preset's limits read back as its word, that one changed limit reads as custom, and that medium equals today's defaults. The docs test already parses the start-input rows against the tool schema, and it gains the size rows. A tool-level test covers how size, model and worker_model reach the swarm, which no test covers today. For power, a run on Copilot with the class map, started at deep, confirms the lead's turns request gpt-6-astra and the card names it.

E · Alternatives not chosen

AlternativeWhy not
Mirror the channel in a drawer boardFrames replace the whole payload, so an open drawer re-sends up to 96 KB per message; rows cannot render markdown and have no scroll anchoring. It builds a second, worse home for a conversation ClickClack already holds, the same reason Chamber removed its exhibits shelf.
A Needs-you banner regionThe banner slot cannot collapse or hide, so it always shows. Chamber moved its Briefing out of the banner for this reason. The index head carries the verdict instead.
A panel per live swarm, or pinned swarmsChamber removed per-room panels: a panel is for what stays true, and you enter what is happening. Each runtime region also makes every client re-fetch the rib list, which re-runs every rib's auth probe.
A Dispatched runs regionA second home for runs that already live on each swarm's drawer, and the Workflows tab already lists runs.
A rib-built run traceDuplicates the host's run view; what is missing is only an effect to open it.
An html transcript, or a ClickClack embedAn html region reloads its iframe on every frame, losing scroll and typing. The sandbox blocks frames and network access, and ClickClack serves its embeds with frame-ancestors 'self'.
Approve and Request changes buttonsDecision D1.
One shared reader keyTwo viewers opening different swarms would race on it; the reading pane is one key per swarm.
A tab titled ChatKeelson already has a Chat tab.
Numbers as the size labelsThree numbers per option read as a spreadsheet; the word carries the choice and the numbers sit one hover or one click away.
Size and power as chip strips with hintsChips carry hover today, as Chamber's scope bar does, but each click is a round trip that toasts <type> ✓, and the choice becomes a draft held on the server and shared by every viewer rather than a value in the form.
Model names as the power labelsNames like flash, sol and astra differ by provider and change as catalogs rotate; the class words stay the same and the hover names the model.

Power that runs the lead a class above workersA single word would then mean two models; the tool's model and worker_model already cover a split.
